# README patterns to choose from

Use these patterns according to the project and reader. Omit what does not help; do not turn this into a mandatory template. A source review of Awesome README's examples and linked README tools informed these choices; observed patterns do not prove traffic or adoption effects.

| Reader need | Useful pattern | Examples |
| --- | --- | --- |
| Recognize the project quickly | One title, direct purpose, a few ordinary badges, text navigation | Markdownify, HTMLHint, Understand Anything |
| Understand a CLI | Real command and output or a short terminal recording | HTTPie, hicat, Supabase Plus |
| Evaluate a library | Small idiomatic code example before detailed API reference | Edlib, Closures, React Tilt |
| Install the right thing | Separate user downloads, source builds, and contributor setup | Bridge, The Lounge, Terminal.Gui |
| Choose among supported routes | One recommended path, then clearly labelled alternatives | Gowebly, Nerd Fonts, Updo |
| Avoid the wrong version | Short migration/branch notice near the opening | dbt, Redoc, Doom Emacs |
| Understand a changed behavior | Matched before/after code, data, or actual output | Array Mixer, Radioactive State, MarkdownToBBCode |
| Navigate a large reference | Short contents, linked docs, disclosure for secondary variants | Spark metrics plugin, QuickSwitch, Size Limit |
| Understand prerequisites and exposure | Explicit provider/runtime/security conditions beside usage | bia-bob, ReviewAid, FileShot |
| Reproduce a result | Input/data source, method, output, limitations, and references | Yampa, OGMA, research projects in the collection |
| Find work in a large repo | Small role-based component/source map with a start path | This My PC, OEIS Tools, architecture projects |
| Keep a demonstration current | Store the recording source and link it to the generated asset | VHS, Terminalizer, ttystudio |

## Native presentation defaults

- Prefer standard flat badges with meaningful destinations. Use ordinary links for docs/demo/navigation; do not fabricate GitHub UI buttons in SVG.
- Use one meaningful visual at a time: actual output, a task recording, a diagram explaining a relationship, or an existing project identity. Do not generate a decorative hero by reflex.
- Keep the title and purpose once. Avoid repeating the same slogan in a banner, heading, subtitle, and feature section.
- Choose normal document headings and readable prose. Use tables for real comparisons or mappings, not to make every paragraph look like a product card.
- Keep the main first-use path open. Use details/summary for optional platform variants, long configuration, or deeper developer material.
- Let short tools have short docs; let conceptual or research work have justified depth. Separate setup from a useful first task, and finish the example at an observable result.
- Treat compatibility and benchmark statements as claims requiring evidence. Name prerequisites and tested conditions; do not inherit a badge or claim from a reference project.

## Review references critically

Find the actual README: case-sensitive root filenames, .github/README, docs READMEs, HTML headings, Setext headings, and reStructuredText can all be valid. Resolve moved repositories and documents. Distinguish the curator's description from the current source, and source review from rendered/browser inspection. Record inaccessible or empty sources rather than guessing.

Do not copy upstream logos, screenshots, identities, or text. Summarize useful patterns with source links and explain which choices were adopted, omitted, or adapted. Keep a research notebook outside the installed skill package; keep only reusable guidance here.

## Optional visual tools

Use available, appropriate tools instead of adding dependencies by default. Gifski and ScreenToGif are examples of capture/export workflows; Terminalizer, ttystudio, and VHS show editable terminal recording sources. Verify current platform support, installation, output, and size before recommending one. Never execute a downloaded installer merely to decorate a README.

Profile statistics, contributor cards, social widgets, and typing SVGs have distinct uses. Do not import them into product READMEs by default. They add external endpoints and maintenance; provide a text/static fallback for essential information and prefer actual user-task evidence.
