## Lessons added to the skill

| Pattern | Apply when | Examples |
| --- | --- | --- |
| Familiar title, short purpose, standard badges, inline links | Most repository openings | Markdownify, HTMLHint, Understand Anything |
| A task and its actual result | Readers need proof before detail | HTTPie, Size Limit, Supabase Plus |
| Tiny code sample before a long API | Libraries and language tools | Edlib, Closures, React Tilt |
| Separate release, source, and contributor paths | Apps and tools offer different entry points | Bridge, The Lounge, Terminal.Gui |
| Recommended route before alternatives | Multiple package managers or hosts | Gowebly, Nerd Fonts, Updo |
| Version/migration notice near the top | A branch or major version changes the right action | dbt, Doom Emacs, Redoc |
| Disclosure for secondary details | Optional config, platforms, or developer internals | Spark metrics plugin, QuickSwitch, Size Limit |
| Claims and requirements beside the example | AI, security, research, and measured comparisons | bia-bob, FileShot, ReviewAid |
| Match depth to the repository | A small utility and an architecture study have different needs | hicat, EventualShop, READMINE |
| Keep the source of a demo | Recordings need to remain reproducible | VHS, Terminalizer, ttystudio |
| Recognize alternate document formats and locations | Source review and link validation | ArminC AutoExec, DVC, academic HTML READMEs |
| Distinguish product documentation from profile decoration | Stats, social cards, and animated titles | GPRM, GitHub Stats Extended, Typing SVG |

These are design choices inferred from source, not instructions to copy every example. Several references also show patterns to use cautiously: badge walls, repeated star requests, prominent sponsor blocks, outdated compatibility text, unsupported speed claims, dependency-heavy profile widgets, and deep reference material before first use.

## Current repository direction

Use GitHub's normal typography and spacing. Use standard flat badges for actual status or documented routes, and ordinary text links for navigation. Make a task, sample output, or real product capture the proof. Add a banner only when it helps identify this particular project; a generated 3D object is not a default requirement.

Hallmark and GPT Taste were used as design inputs for this revision. Their applicable principles are hierarchy, specificity, restraint, readable text, and avoiding repetitive generated layouts. GitHub's rendering constraints take precedence over web-only motion, CSS, or typography recipes.
